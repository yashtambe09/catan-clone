# CATAN Project — Decisions Log
**Repo:** https://github.com/yashtambe09/catan-clone
**Planned domain:** catan.mightyeaption.in (subdomain of an existing domain, ~1.5 yrs remaining on registration)
**Timeline:** 30 days, day-by-day task division (see flow.md)

---

## 1. Project Scope

- Full digital clone of Settlers of Catan, playable by 2–6 players over the internet with friends.
- Full ruleset: trading (bank + player-to-player + ports), development cards, robber, longest road, largest army.
- Standard win condition: **10 VP**, same for all player counts (no house rules on this).
- Two board sizes:
  - **2–4 players:** standard 19-hex board (rows 3-4-5-4-3)
  - **5–6 players:** expanded 30-hex board (rows 3-4-5-6-5-4-3), extra harbors
  - Both generated by one parameterized board-generation function (not two separate hardcoded implementations), keyed off player count.
  - Fairness constraint on generation: no two adjacent hexes both showing 6 or 8; roughly even resource-type distribution.
- App has three functional areas: **signup/login**, **career/stats page**, **the game itself**.

---

## 2. Tech Stack

- **Backend:** Python (FastAPI + python-socketio, or raw `websockets` — decide exact library at scaffold time). Server is fully authoritative; client never trusts its own local state for dice rolls, resource counts, or validation.
- **Frontend:** React + Redux (state management).
- **Real-time layer:** WebSockets (Socket.io-style rooms for lobby/game session scoping).
- **Board rendering:** SVG-based (plain functional first on Day 5, styled later in UI phase).
- **UI component library:** *not yet decided* — deferred to Day 17 (start of UI/UX phase), once the app is functionally real. Candidates discussed: shadcn/ui, Radix UI primitives.
- **Hex-grid math:** consider `react-hexgrid` / `honeycomb-grid` (npm) rather than hand-rolling axial/cube coordinate math from scratch.

---

## 3. Database

- **Postgres, hosted on the same laptop as the backend, in Docker** (not Supabase, not any external managed DB — this was a deliberate decision to avoid an external dependency, accepted the tradeoff explicitly).
- **Auth is hand-rolled** (no Supabase auth): password hashing via `passlib` or `argon2-cffi` (argon2 preferred), sessions/JWT handled in the FastAPI backend. Do not roll custom crypto — use vetted libraries only.
- **Backup strategy:** incremental `pg_dump` on a schedule (daily, or before/after game sessions), dumped to a **location separate from the laptop's disk** (cloud storage / external drive — same-disk backup doesn't protect against disk failure). Retain ~7–14 days, prune older. Restore path must be tested once during setup, not left untested.
- **Known limitation, accepted:** if the laptop/server is off, the DB (and thus login/stats) is unreachable too. This is a friends-only hobby server, not always-on infra — backups protect data integrity, not uptime.

### Schema (draft)
```sql
users (
  id, username UNIQUE, password_hash, created_at
)

games (
  id, started_at, ended_at, winner_id, player_count, board_size
)

game_players (
  game_id, user_id, final_score, placement
)
```
- `game_players` is the key join table — supports both aggregate stats (wins/losses/win-rate) and richer queries (past-opponent history, "games played with X").
- `player_count` / `board_size` columns on `games` added so stats can later be filtered/segmented by board size if wanted.

## 4. Hosting & Networking

- **Frontend (UI):** Cloudflare Pages (static hosting).
- **Backend:** runs on the user's laptop, exposed via **Cloudflare Tunnel** (`cloudflared`) — no inbound ports opened, no home IP exposed directly.
- **Domain:** existing domain, previously used for another (now retired) website, ~1.5 yrs of registration remaining. Reusing it via a new subdomain: `catan.mightyeaption.in`.
- **TLS:** handled automatically by Cloudflare.
- **Access control:** Cloudflare Access (email-gated) or a shared-passphrase gate restricting the subdomain to the friend group — decided to add this as a deliberate security layer given the server is internet-exposed and always-on.
- User has explicitly accepted the tradeoffs of running a personal server exposed to the internet, keeping the laptop on continuously, for this friends-only use case.

---

## 5. Reliability / Non-Functional Requirements

- **Authoritative server, dumb client** — every move (trade, build, dice roll) is validated server-side; client only renders state it's given.
- **Docker resource limits** set explicitly in `docker-compose.yml` early, so resource issues are caught locally, not after deployment.
- **WebSocket state diffing** — send only changed state per update, not the full game state on every tick (matters more at 6 players with full resource/dev-card state).
- **Reconnect / rejoin handling is non-negotiable** — a dropped player (expected on home wifi with 6 friends) must be able to rejoin and receive a full state resync without breaking the game for everyone else. Server holds the seat open.
- **Load testing before deployment:** explicit test days for running full 6-player games locally (not just 2–3 player runs) to catch resource/message-volume issues that don't appear at lower player counts.

## 6. Claude Code Tooling & Workflow

- **CLAUDE.md** written on Day 1: stack, folder structure, coding conventions, test commands, things to avoid. Kept lean (~500 words) and stable — it's loaded every turn, and edits invalidate prompt caching.
- **Model discipline:** Sonnet for routine implementation work; Opus reserved for genuinely hard logic (board fairness algorithm, placement/adjacency rules across both board sizes, longest-road recalculation with branching paths, win-condition + persistence logic). See `flow.md` for the day-by-day model/effort assignment.
- **Plan Mode** used before big features, so Claude scopes a change before touching files.
- **`/context` and `/usage`** checked periodically to see what's actually consuming the context window.
- **Prompt caching** preserved by keeping CLAUDE.md and tool definitions stable within a session — avoid mid-session edits to these.
- **`@file` syntax** used to reference specific files rather than whole directories.

### Graphify (codebase knowledge graph)
- Chosen over "Code Review Graph" — Graphify is the better fit for this project because the bulk of the work through week 2–3 is greenfield *writing* of new game logic, not reviewing large diffs in an established monorepo (which is what Code Review Graph is optimized for).
- Graphify also ingests docs/markdown alongside code, useful for querying rules docs (e.g. a RULES.md) alongside implementation.
- **Install timing:** originally "week 2," refined in `flow.md` to **around Day 14** (once dev cards/longest-road work begins and the codebase is complex enough to benefit).
- **Update mechanism:** Graphify doesn't auto-watch (unlike Code Review Graph), so refresh via a **git post-commit hook** running `graphify update` — this naturally fires whenever a commit lands, rather than a rigid twice-daily cron.
- `.gitignore`: `graph.json`, `GRAPH_REPORT.md` (derived data, not versioned).

### claude-mem (persistent memory) — evaluated, rejected
- Considered alongside Graphify (~Day 14), **not installed**.
- Its installer's memory-provider step offers four options: its own hosted "CMEM Pro" ($30/mo after a 14-day trial), an OpenRouter key, a Gemini key, or "use your Anthropic plan" — the last of which bills against whatever Claude Code account is authenticated in the terminal running it. That account is BETSOL's, not a personal one, and the quoted rate (~$58.91/1k observations, the default Haiku path) is the most expensive of the four. Spending company-billed usage on a personal side project isn't worth it, and the cheaper options still cost real money against a personal key for a hobby project.
- **CLAUDE.md remains the sole persistent-context mechanism** — no dynamic/session memory layer sits alongside it. Keep CLAUDE.md itself current rather than assuming another layer covers gaps.
- Claude Code's built-in **Auto Memory** (writes its own MEMORY.md) is on by default since v2.1.59 and still applies regardless of this decision.
